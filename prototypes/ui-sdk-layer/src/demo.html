Prototype · visual layer for UI SDK

Ripple Layer: one stylesheet that gives UI SDK a storefront look

Everything in the store below is real UI SDK markup (ui-radio-group, ui-number-input, ui-drawer, ui-toast and friends). Ripple adds twelve knobs, maps them onto UI SDK's own --ui-* variables, and tunes each part through the data-slot and state attributes UI SDK already renders. Switch themes, turn the layer off, or drag a knob.

    you write12 knobsPaper, ink, brand, highlight, radius, elevation, density, two fonts, display weight, tracking, case, type scale.
    derived~40 tokensSurfaces, lines, subtle text, focus ring, brand tints, spacing unit, a 9-step type scale, shadows. All color-mix() and calc().
    mappedUI SDK --ui-*All 55 UI SDK components pick up the theme through their own variables, with no per-component work.
    refinedRipple partsStorefront sizing and looks keyed on data-slot and UI SDK state: chips, swatches, cards, stepper, drawer.
    added7 primitivesheading, text, eyebrow, price, badge, card, media. Same data-slot convention.
    escape hatchTailwindLayout and one-offs. Utilities read the same tokens (bg-surface, border-line) and always win the cascade.

    The layer is one CSS file in cascade layers: ui-sdk < ripple < Tailwind utilities. No build step, no JavaScript, and nothing framework-specific, so the same markup works from Liquid, React, Remix or plain HTML. A theme is a block of knobs on data-theme; a section can re-theme itself with data-surface="inverse|brand|muted" (see the announcement bar and the newsletter band).

    Turn on Show parts and hover the store: blue outlines are UI SDK parts and Ripple primitives, orange ones are custom HTML written with Tailwind. The custom pieces still follow every theme because they use token utilities.

    Five rules an agent can hold in its head. Each value list is closed, so a linter can check every attribute.
    
        
      
          
    1. Behavior is UI SDK. If UI SDK has the part, use it. Never rebuild a radio, stepper, drawer or accordion.
      2. 
          
    2. data-slot says what it is. UI SDK sets it on its parts; you set it on the seven primitives.
      3. 
          
    3. data-variant, data-size, data-tone say how it looks. Pick from the table below. State (data-checked, data-open, data-disabled) comes from UI SDK; never fake it with classes.
      4. 
          
    4. Tailwind arranges. Layout, width, position and one-offs are utilities, using token colors (bg-surface, text-subtle, border-line), never raw hex.
      5. 
          
    5. Themes are knobs. Change the look by editing the theme block or a data-surface, never by restyling a part.
      6. 
        
    
        
    
          
    
            
    SlotAttributesUse for
    
            
              
    button (UI SDK)data-variant solid · soft · ghost · link · destructive

    radio-group (UI SDK)data-variant chips · swatches · cardsSize, colour, purchase options. Disabled radio means sold out.

    Five ways to put a look on UI SDK. This prototype is option 2; the layer toggle above shows option 1 against it.
    
        
    
          
    
            
    ApproachGoodCosts
    
            
              
    1. Tokens only. Map knobs onto --ui-*, keep UI SDK's web.css.Tiny (about 40 lines). Never drifts from UI SDK.UI SDK's look is dense app UI: 13px text, 32px controls, a single radius. No chips, swatches or display type, so storefronts look like admin panels.
    
              
    2. Layer on top this one
    Tokens, plus refinements keyed on data-slot, plus a few primitives.    		Storefront look with UI SDK's markup unchanged. One file, no build, any framework. Vocabulary is small and lintable.Depends on UI SDK's slot names and its CSS staying stable; an upstream rename needs a patch. About 700 lines to own.
    
              
    3. Replace web.css. Write every slot rule yourself.Total control; no fighting the default.About 3,000 lines to own across 55 components, and every UI SDK release can add parts you haven't styled.
    
              
    4. Tailwind recipes in markup. shadcn-style class strings on each part.Very visible; agents already know Tailwind; easy one-off edits.Long class strings get copied with drift, themes need class edits instead of knobs, and Liquid templates get noisy.
    
              
    5. Tailwind plugin. Ship variants like rp-chip, data-checked: helpers.Feels native in Tailwind projects.Requires Tailwind and a build; doesn't help plain-CSS or Liquid users. Works best as an add-on to option 2.
