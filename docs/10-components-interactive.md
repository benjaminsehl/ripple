### Purpose

A modal window centred over the page, built on the native `<dialog>` element inside one `rp-dialog` wrapper.

- Use when: short, self-contained content interrupts the page (size guide, confirmation, quick view, search).
- Do not use when: the panel slides in from a screen edge (use Drawer); the content must be readable when JavaScript never loads (use Accordion); the popup is small and anchored to its button (use Popover).

### Anatomy

| Part | Export (TSX) | Liquid file | Element | Class | Hook attribute | Required | Id rule |
|---|---|---|---|---|---|---|---|
| root | `Dialog` | `blocks/dialog.liquid` | `rp-dialog` | `rp-dialog` | `data-slot="rp-dialog"` | yes | none |
| panel | none (printed by `Dialog`) | none (printed by `blocks/dialog.liquid`) | `dialog` | `rp-dialog-panel` | none | yes | `<id>` |
| header | `DialogHeader` | `blocks/dialog-header.liquid` | `div` | `rp-dialog-header` | none | no | none |
| title | `DialogTitle` | `blocks/dialog-title.liquid` | `h2` | `rp-dialog-title` | none | yes | `<id>-title` |
| description | `DialogDescription` | `blocks/dialog-description.liquid` | `p` | `rp-dialog-description` | none | no | `<id>-description` |
| body | `DialogBody` | `blocks/dialog-body.liquid` | `div` | `rp-dialog-body` | none | no | none |
| footer | `DialogFooter` | `blocks/dialog-footer.liquid` | `div` | `rp-dialog-footer` | none | no | none |

Nesting rules:

1. `rp-dialog` MUST contain exactly one child, the `<dialog>`. The `id` is on the `<dialog>`, never on `rp-dialog`.
2. The children of the `<dialog>` are, in this order: header (optional), title (only when there is no header), description (optional), body (optional), footer (optional). No other element may be a child of the `<dialog>`.
3. The title is REQUIRED. It is either a direct child of the `<dialog>` or the first child of the header. There MUST be exactly one title per Dialog.
4. The header contains the title first, then at most one closer (an IconButton with `commandFor="<id>"` and `command="close"`).
5. All free flow content goes inside the body. The body is the only part that scrolls.
6. The footer contains Buttons only.
7. A Dialog root MUST NOT be inside an `<a>`, a `<button>`, a `<label>`, another `<dialog>`, a Popover, or a region that its own content refreshes (D-046 item 5).
8. The Dialog root may be placed anywhere else in `<body>`. It takes no space in the flow.

### Content model

`parts` - the children of `Dialog` are its own parts only: `DialogHeader`, `DialogTitle`, `DialogDescription`, `DialogBody`, `DialogFooter`, in the order of nesting rule 2. `DialogTitle` and `DialogDescription` take text (phrasing content). `DialogHeader` takes one `DialogTitle` and at most one IconButton. `DialogBody` takes any flow content. `DialogFooter` takes Buttons.

### Behaviour with JavaScript

1. A click on any `<button commandfor="<id>" command="show-modal">` opens the dialog with `showModal()`. Natively in browsers with Invoker Commands; through the polyfill of `04-elements.md` 3.3 elsewhere.
2. A click on any `<button commandfor="<id>" command="close">` closes it.
3. An unmodified primary click on any `<a href data-rp-open="<id>">` opens it and does not navigate; a modified click (Ctrl, Meta, Shift, Alt, middle button) navigates (D-009).
4. Escape closes it. A press on the backdrop closes it (`closedby="any"`; in browsers without `closedby`, `rp-dialog` closes it when the click target is the `<dialog>` itself and the pointer is outside the dialog's box).
5. Every open and every close dispatches `openchange` on the `rp-dialog` root with `detail.value` (`true` or `false`) and `detail.reason` (one of `trigger-press`, `close-press`, `escape-key`, `outside-press`, `link-press`, `imperative`). The event does not bubble and is cancelable. A cancelled event puts the dialog back in its previous state.
6. With `data-default-open` the element calls `showModal()` once when it connects; `openchange` fires with `value: true`, reason `imperative`.
7. While the dialog is open the rest of the page is inert (browser behaviour of `showModal()`). Feedback raised while it is open MUST be rendered inside it (a FormMessage with `role="alert"`); code MUST NOT call `toast()` while `document.querySelector("dialog:modal")` is not `null` (D-008 item 7).
8. A navigation started by a link or a form inside or outside the dialog closes it with reason `link-press` when the Navigation API reports it as interceptable. `history.pushState` and `history.replaceState` calls do not close it.
9. After close, focus is on the opener. If the opener was replaced by a node with the same `id`, focus goes to that node.
10. The body scrolls when the content is taller than `100dvh` minus the margins; header and footer stay visible.
11. Page scroll behind the dialog is not locked by Ripple. The component CSS MUST NOT set `overflow` on `<html>` or `<body>`.

Items 1 to 9 are implemented by the browser and by `src/elements/rp-dialog.ts` (`04-elements.md` 9.1); this component adds no code.

### Behaviour without JavaScript

- Browser with Invoker Commands: fully working. Buttons open and close the modal dialog; Escape and (where `closedby` is supported) a backdrop press close it. No event is dispatched.
- Browser without Invoker Commands: the opener button does nothing; the dialog stays closed and its content is not reachable. This is why the level is `degraded`.
- Therefore: content that MUST be reachable without JavaScript MUST NOT exist only in a Dialog. When the dialog has a page equivalent, the opener MUST be `<a href="<page>" data-rp-open="<id>">` (D-009); without JavaScript the link navigates to the page.
- No control is marked `data-rp-js`. Nothing is hidden by Ripple CSS: a closed `<dialog>` is hidden by the browser.
- `defaultOpen` has no effect without JavaScript (the dialog stays closed).
- Manifest: `noJs.level: "degraded"`, `noJs.behavior: "With Invoker Commands in the browser the dialog opens and closes with no script. Without them the opener does nothing; an opener with a page equivalent MUST be a link with data-rp-open."`, `noJs.fallbackHref`: absent (the generic Dialog has no page equivalent).

### Accessibility

- Pattern: native `<dialog>` opened with `showModal()` (APG "Dialog (Modal)"); `checkPattern`: `dialog`.
- Accessible name: REQUIRED. From the title through `aria-labelledby="<id>-title"`. A Dialog without a title is a checker error.
- Focus: on open the browser focuses the first focusable element inside the `<dialog>` (an author MAY put the `autofocus` attribute on another control); when nothing is focusable the `<dialog>` itself is focused. Focus cannot leave the dialog while it is open. On close focus returns to the opener.
- Announcements: None. (The browser announces the dialog and its name when it opens.)

| Key | Action |
|---|---|
| Escape | Closes the dialog; focus returns to the opener |
| Tab / Shift+Tab | Moves focus among the controls inside the dialog only |
| Enter or Space on an opener or closer | Opens or closes |

Rules specific to this file:

1. `display` is set on the panel ONLY under `[open]`. Setting it on a closed `<dialog>` would show the dialog.
2. No `z-index`: a modal dialog is in the browser's top layer.
3. The backdrop colour is `var(--color-overlay)` on `::backdrop`. In an engine where `::backdrop` does not inherit custom properties (UNVERIFIED which versions; SPIKE-06) the backdrop is transparent; the panel keeps its border and shadow, and the dialog stays modal.
4. Entrance and exit use `@starting-style` and `transition-behavior: allow-discrete`; an engine without them shows and hides the dialog instantly.

### Purpose

A modal panel that slides in from an edge of the screen. It is the same element and the same native `<dialog>` as Dialog, with different classes and a `side` prop. CartDrawer and MobileNav are built on it.

- Use when: a tall or long-lived panel is needed beside the page (filters, cart, navigation, a long form).
- Do not use when: the content is short and centred (use Dialog); the popup is small and anchored to its button (use Popover); the content is the cart or the mobile menu (use CartDrawer or MobileNav, which already compose Drawer).

Nesting rules:

1. `rp-dialog` MUST contain exactly one child, the `<dialog>`. The `id` is on the `<dialog>`. `data-slot` is `rp-dialog` (the tag name), not `rp-drawer`.
2. The children of the `<dialog>` are, in this order: header (optional), title (only when there is no header), description (optional), body (optional), footer (optional). No other element may be a child of the `<dialog>`, with one exception: components built on Drawer MAY print one live region `<div role="status" data-rp-part="status"></div>` directly after the header (`04-elements.md` 3.5; used by CartDrawer).
3. The title is REQUIRED, exactly once, as a direct child of the `<dialog>` or as the first child of the header.
4. The header contains the title first, then at most one closer (an IconButton with `commandFor="<id>"` and `command="close"`).
5. All free flow content goes inside the body. The body is the only part that scrolls. A refreshable region (`data-rp-region`) that the drawer's content refreshes MUST be inside the body; the Drawer root MUST NOT be inside that region (D-046 item 5).
6. The footer contains Buttons or a CheckoutButton, stacked in one column.
7. A Drawer root MUST NOT be inside an `<a>`, a `<button>`, a `<label>`, another `<dialog>` or a Popover.

### Behaviour with JavaScript

Identical to Dialog, "Behaviour with JavaScript", items 1 to 11, with "dialog" read as "drawer". In addition:

1. `side="end"` attaches the panel to the inline-end edge at full viewport height; `side="start"` to the inline-start edge; `side="bottom"` to the bottom edge at full width with a maximum height of `85dvh`. In a right-to-left document `start` and `end` swap sides.
2. Entrance and exit are a slide from the attached edge (`translate`), 300 ms in and 200 ms out with `--ease-drawer`; with `prefers-reduced-motion: reduce` the panel appears and disappears instantly.
3. A region refresh inside the body (`rp:refresh`) does not close the drawer (`04-elements.md` 9.1 item 7).

### Behaviour without JavaScript

- A Drawer opened by `<a href="<page>" data-rp-open="<id>">`: the link navigates to the page. Full function through the page. This is the REQUIRED opener when a page equivalent exists (D-009): cart drawer and `/cart`, mobile nav and the footer menu anchor, search and `/search`, a filter drawer and the collection URL with the filter form printed in the page.
- A Drawer opened by a `commandfor` button: works in browsers with Invoker Commands; in other browsers the button does nothing and the content is not reachable.
- No control is marked `data-rp-js`. `defaultOpen` has no effect without JavaScript.
- Manifest: `noJs.level: "degraded"`, `noJs.behavior: "With Invoker Commands the drawer opens and closes with no script. Without them a button opener does nothing; an opener with a page equivalent MUST be a link with data-rp-open, which navigates."`, `noJs.fallbackHref`: absent on the generic Drawer (CartDrawer and MobileNav set it).

## Popover

### Purpose

A small non-modal panel that opens next to the button that controls it and closes on Escape or on a press outside. It is the native `popover` attribute plus CSS; Ripple ships no JavaScript for it (D-010).

- Use when: a short piece of secondary content or a short list of links and actions belongs to one button (shipping details, a sort list, an account menu, order actions).
- Do not use when: the content needs the user's full attention or contains a long form (use Dialog); the panel is tall or attached to a screen edge (use Drawer); the content is a one-line hint for a control (use Tooltip); the items are site navigation with sublevels (use NavigationMenu).

### Anatomy

| Part | Export (TSX) | Liquid file | Element | Class | Hook attribute | Required | Id rule |
|---|---|---|---|---|---|---|---|
| root | `Popover` | `blocks/popover.liquid` | `div` | `rp-popover` | none | yes | `<id>` |
| title | `PopoverTitle` | `blocks/popover-title.liquid` | `p` | `rp-popover-title` | none | no | none |

Nesting rules:

1. The root carries the `id` and the bare `popover` attribute.
2. The title, when present, MUST be the first child of the root and MUST appear at most once. It is a visual heading only; it is not referenced by any ARIA attribute.
3. Everything else inside the root is free flow content: text, Links, Buttons, a LinkList, form controls.
4. A Popover root MUST NOT be inside an `<a>`, a `<button>` or a `<label>`. It MAY be inside a `<dialog>` and inside another Popover (the browser keeps the outer one open).
5. A Popover MUST NOT contain a Dialog or Drawer root (`dialog-not-nested`, `drawer-not-nested`).
6. The opener is a Button or IconButton with `popoverTarget="<id>"`, placed by the author directly BEFORE the root in document order whenever the layout allows it, so that the keyboard order is opener, then panel content.

### Behaviour with JavaScript

Identical to "Behaviour without JavaScript": no Ripple script reads or writes a Popover. The only script that can be involved is the Invoker Commands polyfill of `04-elements.md` 3.3, and only when the opener uses `commandfor` with `command="toggle-popover"`, `"show-popover"` or `"hide-popover"` instead of `popovertarget`. Authors MUST prefer `popovertarget`, which needs no polyfill.

### Behaviour without JavaScript

1. A press on the opener toggles the panel. The panel is shown in the top layer.
2. Escape, a press outside the panel, or opening another auto popover that is not nested inside this one closes it. A button inside the panel with `popovertarget="<id>"` and `popovertargetaction="hide"` closes it.
3. Position, in browsers with CSS anchor positioning: the panel is placed against its implicit anchor, which is the button that opened it. `data-side` chooses the edge of the button (`top`, `bottom`: block axis; `start`, `end`: inline axis, mirrored in a right-to-left document). `data-align` chooses the alignment along that edge (`start`: start edges aligned; `center`: centred; `end`: end edges aligned). The gap to the button is `--rp-popover-offset`. When the panel does not fit, the browser tries the opposite side, then the opposite alignment, then both (`position-try-fallbacks`).
4. Position, in browsers without CSS anchor positioning (the rules are inside `@supports (anchor-name: --a)`): the user-agent default applies and the panel is centred in the viewport. It stays fully usable.
5. In a browser without the Popover API the panel is ordinary content in the page flow and the opener does nothing (`04-elements.md` Ledger issues L-8). Content is readable; nothing is hidden. According to public compatibility tables (not run) this includes browsers AT the floor of D-027: the API arrived in Chrome 114, Safari 17.0 and Firefox 125. Because of this, a Popover MUST NOT contain content that is harmful when always visible (for example a second copy of a form with the same field ids).
6. Entrance and exit: opacity fade of `--rp-duration-base`, only inside `@supports selector(:popover-open)` and `prefers-reduced-motion: no-preference`.
7. No control is marked `data-rp-js`.
8. Manifest: `noJs.level: "degraded"`, `noJs.behavior: "Opens and closes natively with no script. Without CSS anchor positioning the panel is centred in the viewport instead of placed next to its button. Without the Popover API the panel is always-visible content in the page flow."`, `noJs.fallbackHref`: absent.

### Accessibility

- Pattern: native popover with a button invoker (disclosure semantics supplied by the browser); `checkPattern`: `null`.
- Accessible name: not applicable. The root has no role and MUST NOT be given `aria-label` or `aria-labelledby`. The opener MUST have an accessible name (text, or `ariaLabel` on IconButton).
- Focus: opening does not move focus; it stays on the opener. The browser inserts the panel's focusable content into the Tab order directly after the opener. When the panel closes while focus is inside it, the browser returns focus to the opener.
- Announcements: None. The browser exposes the opener's expanded state.

| Key | Action |
|---|---|
| Enter or Space on the opener | Toggles the panel |
| Tab from the opener while open | Moves to the first focusable element in the panel |
| Escape | Closes the panel; focus returns to the opener when it was inside the panel |

There is no `role="menu"`, no `role="menuitem"` and no arrow-key roving (D-018). Items in an action list are reached with Tab.

|---|---|

### Purpose

A one-line text hint that appears next to a button on hover and on keyboard focus. It is the UI SDK tooltip (`ui-tooltip`), loaded lazily, with the closed state pre-rendered by the server (D-013).

- Use when: an icon-only or terse button benefits from a short description that is also available somewhere else, or is not needed to complete a task.
- Do not use when: the text is needed to complete a task or must be reachable on touch screens and without JavaScript (print it as visible Text, or use Popover); the hint contains a link, a button or more than one sentence (use Popover); the control is a link (`<a href>`), which V1 does not support as a trigger.

### Anatomy

| Part | Export (TSX) | Liquid file | Element | Class | Hook attribute | Required | Id rule |
|---|---|---|---|---|---|---|---|
| root | `Tooltip` | `blocks/tooltip.liquid` | `ui-tooltip` | `rp-tooltip` | none | yes | `<id>` |
| trigger | `TooltipTrigger` | `blocks/tooltip-trigger.liquid` | `ui-tooltip-trigger` | none | none | yes | none |
| content | `TooltipContent` | `blocks/tooltip-content.liquid` | `ui-tooltip-content` | `rp-tooltip-content` | `data-slot="tooltip-content"` | yes | `<id>-content` |

Nesting rules:

1. The root contains exactly two children, in this order: the trigger part, then the content part.
2. The trigger part contains exactly ONE element: a native `<button type="button">`. In real pages it is a Button or IconButton WITHOUT `href`. It MUST NOT be an `<a>`: UI SDK writes `type="button"` on a link trigger at upgrade (a mutation and an invalid attribute; evidence below).
3. That button MUST carry `aria-describedby="<id>-content"` and `data-slot="tooltip-trigger"`. The author passes both through the button's rest props (Liquid: `attributes`). It MUST have its own accessible name (visible text, or `ariaLabel` on IconButton). The tooltip text MUST NOT be the button's only name.
4. The content part contains text only. No element children, no links, no buttons.
5. The trigger part has no class because it is `display: contents` (`base.css`) and has no box to style. This is the same exception as `ui-tabs-tab`.
6. A Tooltip root MUST NOT be inside an `<a>`, a `<button>` or a `<label>`.
7. A button that opens a Dialog, Drawer or Popover MAY be a tooltip trigger (it keeps its `commandfor` or `popovertarget`).

### Behaviour with JavaScript

1. Loading: the `tooltip` chunk is loaded by the lazy loader of `04-elements.md` 3.2 when the page contains a `ui-tooltip`. Until it has loaded the trigger works as an ordinary button and no tooltip shows.
2. Upgrade writes nothing inside the root (verified for a button trigger with the attributes of the contract).
3. Hover: when the pointer rests on the trigger for 600 ms (UI SDK default `delay`; Ripple sets no `delay` attribute) the content is shown. When another tooltip is open or was open a moment before, the next one opens at once. It closes when the pointer leaves the trigger (UI SDK default `closeDelay` 0).
4. Keyboard focus: the content is shown at once when the trigger receives keyboard focus, and closes on blur.
5. Escape closes the tooltip and does nothing else (it does not close a Dialog that contains the trigger while the tooltip is open; UNVERIFIED, covered by acceptance test 8).
6. Activating the trigger performs the button's own action (for example `commandfor`) and closes the tooltip.
7. Position: UI SDK places the content in the top layer next to the trigger on `side` with `align`, flips when there is no room, and writes the result as `data-side` / `data-align`. `start` and `end` follow the writing direction.
8. The content has `pointer-events: none`: it cannot be hovered or selected.
9. Motion: an opacity fade of `--rp-duration-fast` through `[data-starting-style]` and `[data-ending-style]`, only under `prefers-reduced-motion: no-preference`.
10. Touch: there is no hover. Whether a tap shows the tooltip through focus is UNVERIFIED and MUST NOT be relied on. The UI SDK option `toggleable` is not used in V1.
11. `openchange` is dispatched on `ui-tooltip` for every open and close.

### Behaviour without JavaScript

- The tooltip never shows. The content stays `hidden`.
- The trigger keeps its accessible name and its own action. Assistive technology still reads the description, because `aria-describedby` references are resolved for hidden elements.
- Sighted users without JavaScript, and touch users, do not see the text. Therefore the tooltip text MUST NOT be the only place where information needed to complete a task appears.
- No control is marked `data-rp-js`.
- Manifest: `noJs.level: "none"`, `noJs.behavior: "The tooltip never shows. The trigger keeps its name and action; the description is still exposed to assistive technology through aria-describedby."`, `noJs.fallbackHref`: absent.

### Purpose

The page's single, empty notification region plus the `toast()` function that shows a short, self-dismissing message in it after a client-side action. The region is the UI SDK `ui-toast-region`, loaded lazily (D-013).

- Use when: an action that completed WITHOUT a page load needs a brief confirmation or error ("Added to cart", "Could not update quantity") and the result is also visible elsewhere on the page.
- Do not use when: the message is produced by the server or must survive a reload (use Banner); the message belongs to a form or a field (use FormMessage); the message needs a decision (use Dialog); a modal dialog is open (announce through its `data-rp-part="status"` region, `04-elements.md` 3.5).

### Anatomy

Nesting rules:

4. Elements that UI SDK creates inside the root at run time are not parts of the contract and carry no class: `<ol data-slot="toast-list">` and, per toast, `ui-toast`, `ui-toast-title`, `ui-toast-description`, `ui-toast-close` (structure under "Behaviour with JavaScript").

### Behaviour with JavaScript

1. Loading: the `toast` chunk is NOT loaded at page load. `toast()` loads it on first use (`04-elements.md` 10.6 rule 3). The region is inert until then.
2. Showing a message is only possible through the helper:

   ```ts
   import { toast } from "<pkg>/elements"; // Liquid themes: import { toast } from "ripple"

   await toast("Added to cart", { description: "Linen shirt, size M", type: "success", duration: 5000 });
   ```

   Signature: `toast(title: string, options?: ToastOptions): Promise<void>`. `ToastOptions` is exactly `{ id?: string; description?: string; type?: "default" | "success" | "error" | "warning" | "info" | "loading"; duration?: number; priority?: "polite" | "assertive" }`. `duration` is milliseconds. The source of the helper is owned by `04-elements.md`.
3. The promise resolves after UI SDK has accepted the message. When the chunk cannot be loaded, or the document has no `ui-toast-region`, the promise resolves and nothing is shown; the helper MUST NOT throw.
4. DOM that UI SDK renders for one message (from `uisdk/packages/web/src/toast.ts`, function `fromData`), inside `<ol data-slot="toast-list">`:

   ```html
   <ui-toast toast="<id>" role="listitem">
     <div>
       <ui-toast-title>Added to cart</ui-toast-title>
       <ui-toast-description>Linen shirt, size M</ui-toast-description>
     </div>
     <ui-toast-close><button type="button"></button></ui-toast-close>
   </ui-toast>
   ```

   These elements have no Ripple class. `toast.css` styles them as `.rp-toast :where(<tag>)`. Action buttons inside a toast (`ui-toast-action`) are not supported in V1: `ToastOptions` has no `action`.
5. A message is removed after its `duration` (UI SDK default when omitted), or when its close button is pressed. Timers pause while the pointer is over the region or focus is inside it (UI SDK behaviour; agent action `pause`).
6. Calling `toast()` with the `id` of a message that is still shown replaces that message instead of adding one (UI SDK behaviour, UNVERIFIED in a browser).
7. Callers MUST NOT call `toast()` while a modal dialog is open (`04-elements.md` 9.1 item 9): commerce elements test `document.querySelector("dialog:modal")` and use the dialog's status region instead.
8. Rules for message text: `title` at most 60 characters, no trailing full stop, no HTML (the helper passes text, not markup). An `error` toast MUST be accompanied by a persistent message at the place of the error (FormMessage or the `data-rp-part="error"` element of the commerce component): a toast alone is never the only report of a failure.
9. Position: UI SDK places the region at `side` / `align` of the viewport in the top layer. `start` and `end` follow the writing direction.

### Behaviour without JavaScript

- The region is empty and takes no space. No toast can exist.
- Every flow that would call `toast()` is a native form post or link without JavaScript, and the page that loads next shows the result (cart page, Banner, FormMessage).
- No control is marked `data-rp-js`.
- Manifest: `noJs.level: "none"`, `noJs.behavior: "The region stays empty. Actions that would toast reload a page that shows the result."`, `noJs.fallbackHref`: absent.

### Purpose

A row of tab buttons that shows one panel of content at a time. It is the UI SDK tabs (`ui-tabs`), loaded lazily, with the complete selected state pre-rendered by the server so that the upgrade changes nothing (D-012).

- Use when: two to six peer sections of comparable content share one place and reading all of them at once is not needed (product details / shipping / reviews).
- Do not use when: every section must be reachable without JavaScript in every browser, or be found by in-page search (use Accordion); the sections are pages (use Links, or NavigationMenu); there are more than six sections or the labels are long (use Accordion).

### Anatomy

| Part | Export (TSX) | Liquid file | Element | Class | Hook attribute | Required | Id rule |
|---|---|---|---|---|---|---|---|
| root | `Tabs` | `blocks/tabs.liquid` | `ui-tabs` | `rp-tabs` | `data-slot="tabs"` | yes | `<id>` |
| list | `TabsList` | `blocks/tabs-list.liquid` | `ui-tabs-list` | `rp-tabs-list` | `data-slot="tabs-list"` | yes | none |
| tab | `TabsTab` | `blocks/tabs-tab.liquid` | `ui-tabs-tab` wrapping one `button` | `rp-tabs-tab` (on the `button`; `ui-tabs-tab` has no class) | `data-slot="tabs-tab"` (on the `button`) | yes, at least two | `<id>-tab-<value>` (on the `button`) |
| panel | `TabsPanel` | `blocks/tabs-panel.liquid` | `ui-tabs-panel` | `rp-tabs-panel` | `data-slot="tabs-panel"` | yes, one per tab | `<id>-panel-<value>` (printed on the selected panel only) |

Nesting rules:

1. The children of the root are, in this order: exactly one list, then the panels. Nothing else.
2. The list contains only tab parts. There MUST be at least two tabs.
3. Every tab has exactly one panel with the same `value`, and every panel has exactly one tab. Panels are in the same order as their tabs.
4. Exactly one tab and its panel are selected in server HTML: the pair whose `value` equals the root's `defaultValue`. The author passes `selected` to BOTH parts of that pair (no context, `06-bindings.md` S-7).
5. A tab contains text, optionally with an Icon. It MUST NOT contain interactive content.
6. A panel contains any flow content. A panel MAY contain an Accordion; it MUST NOT contain another Tabs root with the same `id`.
7. Orientation is horizontal only in V1. Every element that carries `data-orientation` prints `horizontal`.

### Behaviour with JavaScript

1. Loading: the `tabs` chunk is loaded by the lazy loader when the page contains a `ui-tabs`. Before it has loaded, the selected panel is visible and the tab buttons are focusable but do nothing.
2. Upgrade: the only record is the same-value `role` write of the allow-list. No attribute changes value; no node is added or removed; the selected panel does not change.
3. A click on a tab selects it: the attributes of "State and attributes" move to the new pair, the previous panel gets `hidden`, the new panel loses it.
4. Keyboard, focus on a tab: ArrowRight and ArrowLeft move focus to the next and previous tab and select it at once (UI SDK default `activation: "automatic"`), wrapping at the ends (default `loop: true`); Home and End go to the first and last tab. In a right-to-left document the arrow keys are mirrored (UI SDK behaviour; UNVERIFIED).
5. Tab from the selected tab moves focus to the selected panel (`tabindex="0"`), then into its content.
6. `valuechange` is dispatched on `ui-tabs` BEFORE the selection changes; a listener that calls `preventDefault()` keeps the current tab selected.
7. Setting the property `ui-tabs.value` selects silently: no event (D-023 item 1). The React binding uses this for the controlled `value` prop.
8. The selected value is not written to the URL and is not restored on reload: after a reload the `defaultValue` tab is selected.
9. There is no motion on panels. The tab indicator colour fades over `--rp-duration-fast` under `prefers-reduced-motion: no-preference`.

### Behaviour without JavaScript

- In browsers that support `@media (scripting: none)` and have scripting disabled: the tab list is not displayed and EVERY panel is displayed, one below the other, in document order. This comes from the block that section 0.3 item 1 adds to `css/base.css`:

  ```css
  @media (scripting: none) {
    ui-tabs-panel[hidden] {
      display: block !important;
    }
    ui-tabs-list {
      display: none !important;
    }
  }
  ```

  It MUST be in `@layer ui-sdk`, in `base.css`, not in `tabs.css`: the rule that hides `[hidden]` elements is `!important` in layer `ui-sdk` (D-021 item 2), and among `!important` declarations an EARLIER layer wins, so no `!important` rule in `rp.components` can override it (measured: `ripple/docs/research/spikes/components-interactive/t.mjs`). Inside the same layer, `ui-tabs-panel[hidden]` (specificity 0,1,1) beats the `:where()` rule (0,0,0).
- Because the tab list is hidden, panels lose their visible labels. A panel whose content is not self-explanatory MUST therefore start with its own heading or lead sentence.
- `tabs.css` adds `padding-block-end: var(--rp-tabs-gap)` to each panel under the same media query, to separate the stacked panels.
- In a browser with scripting disabled that does not support the media feature, and in a browser where the script failed to load (scripting is enabled, so the media query does not match): only the `defaultValue` panel is readable. Content that must always be reachable belongs in an Accordion.
- No control is marked `data-rp-js`.
- Manifest: `noJs.level: "degraded"`, `noJs.behavior: "With scripting disabled every panel is shown in order and the tab list is hidden. Where @media (scripting: none) is unsupported only the default panel is readable."`, `noJs.fallbackHref`: absent.

### Purpose

A vertical list of headings that each show or hide a section of content. Every item is a native `<details>` element; Ripple ships no JavaScript for it (D-011).

- Use when: several sections of secondary content should be scannable by heading and each must be reachable without JavaScript and by in-page search (FAQ, product details, footer link groups on small screens, filter groups).
- Do not use when: exactly one of a few peer sections is always shown and the labels fit in a row (use Tabs); the content is a floating panel (use Popover); a single "read more" toggle is needed (use one `<details>` with Text, not an Accordion).

### Anatomy

| Part | Export (TSX) | Liquid file | Element | Class | Hook attribute | Required | Id rule |
|---|---|---|---|---|---|---|---|
| root | `Accordion` | `blocks/accordion.liquid` | `div` | `rp-accordion` | none | yes | `<id>` (only when `id` is passed) |
| item | `AccordionItem` | `blocks/accordion-item.liquid` | `details` | `rp-accordion-item` | none | yes, at least one | none |
| trigger | `AccordionTrigger` | `blocks/accordion-trigger.liquid` | `summary` | `rp-accordion-trigger` | none | yes, one per item | none |
| content | `AccordionContent` | `blocks/accordion-content.liquid` | `div` | `rp-accordion-content` | none | yes, one per item | none |

Nesting rules:

1. The children of the root are items only.
2. An item contains exactly two children, in this order: one trigger, one content.
3. The trigger contains text (phrasing content). It MAY contain one heading element (`<h2>` to `<h6>`) wrapping the text, written by the author with Heading, when the accordion is part of the page outline. It MUST NOT contain a link, a button or a form control.
4. The content contains any flow content, including another Accordion.
5. With `type="single"`: the root MUST have an `id`; EVERY item MUST receive `accordion="<id>"`; at most one item may have `defaultOpen`.
6. With `type="multiple"`: items MUST NOT receive `accordion`; any number of items may have `defaultOpen`.
7. The chevron is drawn by CSS (`::after` on the trigger). The author MUST NOT add an icon for it.

### Behaviour with JavaScript

Identical to "Behaviour without JavaScript": no Ripple script reads or writes an Accordion. React and Remix bindings add no behaviour (see "Host notes" for how they avoid resetting `open`).

### Behaviour without JavaScript

1. A press on a trigger toggles its item. The browser adds or removes `open` and exposes the expanded state.
2. `type="single"`: the items share `name="<id>"`, so opening one closes the open one (native exclusive accordion). The open item can also be closed, leaving none open.
3. `type="multiple"`: items are independent.
4. In-page search opens a closed item that contains a match, in browsers that auto-expand `<details>` (Chromium; other engines UNVERIFIED).
5. There is no height animation: the content appears and disappears at once. Only the chevron rotates (`--rp-duration-base`, under `prefers-reduced-motion: no-preference`).
6. In a browser without support for `name` on `<details>` (according to public compatibility tables, not run: it arrived in Chrome 120, Safari 17.2 and Firefox 130, all newer than the floor of D-027; SPIKE-06) several items of a `single` accordion can be open at once. Nothing else changes.
7. No control is marked `data-rp-js`.
8. Manifest: `noJs.level: "full"`, `noJs.behavior: "Native <details>: every item opens and closes with no script."`, `noJs.fallbackHref`: absent.

### Accessibility

- Pattern: native `<details>` / `<summary>` disclosure; `checkPattern`: `null` (the UI SDK patterns `accordion` and `disclosure` expect `aria-expanded` buttons, which a `<summary>` does not have).
- Accessible name: each trigger is named by its text, REQUIRED (a trigger MUST NOT be empty). The root has no role and no name.
- Focus: each trigger is a tab stop. Toggling does not move focus.
- Announcements: None. The browser exposes "expanded" / "collapsed" on the trigger.

| Key | Action |
|---|---|
| Tab / Shift+Tab | Next / previous trigger, and focusable content of open items |
| Enter or Space | Toggles the focused item |

There are no arrow-key shortcuts between triggers (the APG marks them optional; native `<details>` has none).

### Purpose

A horizontally scrolling list of items with CSS scroll snapping, plus Previous and Next buttons added by `rp-carousel` (D-016). Scrolling, snapping, touch and keyboard scrolling are native; the element only pages the list and keeps the two buttons' `disabled` state in step with the scroll position.

- Use when: a row of peer items (product cards, images, testimonials) is longer than the available width and seeing all of them is optional.
- Do not use when: every item must be seen (use Grid); the items are the media of one product (use ProductGallery, which composes `rp-carousel`); the content must advance by itself (V1 has no auto-rotation, by decision); there are fewer items than columns at every breakpoint (use Grid).

### Behaviour with JavaScript

The behaviour of `rp-carousel` is specified in `04-elements.md` 9.2 (items 1 to 7 there). Summary of what a user sees:

1. At upgrade the two buttons become visible (they were `visibility: hidden` and kept their space, so nothing moves). The next button gets `disabled` when all items fit.
2. A press on Next or Previous scrolls the viewport by one viewport width in the inline direction, smoothly, or instantly under `prefers-reduced-motion: reduce`. Scroll snapping decides the resting position, so an item is never cut at the start edge.
3. The buttons' `disabled` state follows the scroll position on every scroll and on every resize of the root.
4. `indexchange` is dispatched on `rp-carousel` when the index of the first visible item changes, whatever caused the scroll. It cannot be vetoed.
5. In a right-to-left document the first item is at the right, Next scrolls to the left, and both chevrons are mirrored by CSS (`scale: var(--rp-dir) 1`).
6. The element never moves focus, never hides an item, and never scrolls by itself (no auto-rotation, no looping).
7. A region refresh that replaces items (`rp:refresh` in a surrounding region) needs no action: the element reads the items at event time (`04-elements.md` rule R-5).

### Behaviour without JavaScript

- The list scrolls and snaps by touch, trackpad, mouse wheel with Shift, and keyboard (the viewport is focusable; arrow keys scroll it). All items are reachable.
- The Previous and Next buttons are invisible but keep their space: the generated rule `rp-carousel:not(:defined) [data-rp-js="inflow"] { visibility: hidden }` (`03-styling-and-tokens.md`; `04-elements.md` 10.16 C-4). Nothing shifts at upgrade.
- The scrollbar is hidden by `scrollbar-width: none`; pointer users without a wheel or trackpad and without JavaScript can still scroll by focusing the viewport and using the keyboard. This is the reason the level is `degraded` and not `full`.
- Manifest: `noJs.level: "degraded"`, `noJs.behavior: "The list scrolls and snaps natively. The Previous and Next buttons are hidden until rp-carousel is defined."`, `noJs.hideUntilDefined: ["[data-rp-part=\"prev\"]", "[data-rp-part=\"next\"]"]`, `noJs.fallbackHref`: absent.

### Accessibility

- Pattern: APG "Carousel", basic variant without auto-rotation and without slide picker; `checkPattern`: `null`.
- Accessible name: REQUIRED on the root, from `ariaLabel`. The root is `role="group"` with `aria-roledescription="carousel"`. The two buttons are named by `previousLabel` / `nextLabel`. The viewport keeps its native list role, so assistive technology announces the number of items; items are not given a "slide" role description.
- Focus: tab order is Previous, the viewport (`tabindex="0"`, so that keyboard users can scroll it), the focusable content of the items in document order, then Next. Pressing a button does not move focus. When a button becomes `disabled` while focused, focus stays on it (a disabled button that already has focus keeps it in all engines; UNVERIFIED outside Chromium) and the other button remains reachable with Tab.
- Announcements: None. There is no live region: the list does not change by itself, and after a button press the user reads the newly visible items in the list.

|---|---|
| Tab | Previous button, viewport, item content, Next button |
| ArrowRight / ArrowLeft on the viewport | Native scrolling of the list (mirrored in right-to-left) |

### Purpose

A native number input with a Decrease and an Increase button, wrapped in `rp-quantity` (D-015). The input is a real form control: it submits with its form and works without JavaScript; the element adds the two buttons' behaviour, clamping, and a spoken announcement of the new value.

- Use when: the shopper chooses how many units to add to the cart or changes the quantity of a cart line.
- Do not use when: the number is not a count of items (use Input with `type="number"`); the choice is among a few fixed values (use Select or RadioGroup); the range is continuous (V1 has no Slider; use Input).

### Anatomy

| Part | Export (TSX) | Liquid file | Element | Class | Hook attribute | Required | Id rule |
|---|---|---|---|---|---|---|---|
| root | `QuantityInput` | `blocks/quantity-input.liquid` | `rp-quantity` | `rp-quantity` | `data-slot="rp-quantity"` | yes | `<id>` (only when `id` is passed) |
| decrement | none (printed by `QuantityInput`) | none (printed by the block) | `button` | `rp-quantity-button` | `data-rp-part="decrement"`, `data-rp-js="inflow"` | yes | none |
| input | none (printed by `QuantityInput`) | none (printed by the block) | `input` | `rp-quantity-input` | `data-rp-part="input"`, `data-rp-field="quantity"` | yes | none |
| increment | none (printed by `QuantityInput`) | none (printed by the block) | `button` | `rp-quantity-button` | `data-rp-part="increment"`, `data-rp-js="inflow"` | yes | none |

Nesting rules:

1. The root contains exactly three children, in this order: decrement button, input, increment button. The component prints all three; the author passes no children.
2. The root class and the part class prefix are `rp-quantity`, not `rp-quantity-input` (D-015 fixes the root class). The CSS file is still `components/quantity-input/quantity-input.css`.
3. The root MUST be inside the `<form>` it submits with, or the `form` prop MUST name that form's id.
4. The root MUST NOT be inside an `<a>` or a `<button>`. It MAY be inside a `<label>`-less Field; the accessible name always comes from `ariaLabel`.

Rules the server applies to the initial state (all hosts, same arithmetic):

1. The decrement button prints `disabled` when `disabled` is true OR `defaultValue <= min`.
2. The increment button prints `disabled` when `disabled` is true OR (`max` is passed AND `defaultValue >= max`).
3. The server prints the numbers as given. It does not clamp `defaultValue` into `[min, max]` and does not snap it to the step grid; the caller MUST pass a valid value (the checker reports a literal that is not, RP101).
4. When several QuantityInputs for the same cart line or product are on one page (for example in the page and in a drawer), each one is independent; keeping them in step is the job of the commerce component around them (`11-components-commerce.md`).

### Behaviour with JavaScript

The behaviour of `rp-quantity` is specified in `04-elements.md` 8.2 (items 1 to 7) with complete source in 8.4. Summary of what a user sees:

1. At upgrade the two buttons become visible (they were `visibility: hidden` and kept their space). With the server rules above the upgrade writes nothing.
2. A press on Increase or Decrease changes the value by `step`, clamped to `[min, max]` and snapped to the step grid that starts at `min`. The input shows the new value; the buttons' `disabled` state is updated; the new value is announced as "`<aria-label of the input>` `<value>`" through the announcer of `04-elements.md` 3.5.
3. After its own write the element dispatches bubbling `input` and `change` events on the input, so a surrounding form or commerce element (`rp-product-form`, `rp-cart-line`) sees the change exactly as if the user had typed it.
4. Typing a number and committing it (blur or Enter) normalises it the same way; typing 99 with `max="5"` shows 5.
5. `valuechange` is dispatched on `rp-quantity` BEFORE the value changes. `preventDefault()` vetoes: the input shows the previous value again.
6. Setting the property `rp-quantity.value` is silent (no `valuechange`); the React binding uses it for the controlled `value` prop.
7. A disabled input disables both buttons and ignores steps.
8. A region refresh that replaces the input (`rp:refresh`) needs no action: the element reads the input at event time (`04-elements.md` rule R-5).

### Behaviour without JavaScript

- The number input works: the user types a quantity, the browser validates it against `min`, `max` and `step` on submit, and the value is submitted with the form under `name`.
- The Decrease and Increase buttons are invisible but keep their space: generated rule `rp-quantity:not(:defined) [data-rp-js="inflow"] { visibility: hidden }` (`04-elements.md` 10.16 C-4). Nothing shifts at upgrade.
- The browser's own spin buttons are hidden by CSS in both states (`appearance: textfield`), so that the control looks the same before and after upgrade. ArrowUp and ArrowDown on the focused input still step the value natively.
- Manifest: `noJs.level: "degraded"`, `noJs.behavior: "The number input works and submits. The Decrease and Increase buttons are hidden until rp-quantity is defined."`, `noJs.hideUntilDefined: ["[data-rp-part=\"decrement\"]", "[data-rp-part=\"increment\"]"]`, `noJs.fallbackHref`: absent.

### Accessibility

- Pattern: native `<input type="number">` (exposed as a spin button by the browser) with two helper buttons; `checkPattern`: `null`.
- Accessible name: REQUIRED on the input, from `ariaLabel` (default "Quantity"). When several QuantityInputs are on one page (cart lines) the caller MUST pass a distinguishing `ariaLabel`, `decreaseLabel` and `increaseLabel` that include the product title (fixture `line`). The component does not use a `<label>` element.
- Focus: tab order is Decrease, input, Increase. A button press keeps focus on the button. When a button becomes `disabled` while focused, focus stays where it is; the user continues with Tab.
- Announcements: after a button press the element announces "`<input name>` `<value>`" politely (for example "Quantity 3"). Typing is not announced (the screen reader already echoes it).

| Key | Action |
|---|---|
| Tab / Shift+Tab | Decrease button, input, Increase button |
| ArrowUp / ArrowDown on the input | Native step up / down by `step` |
| Enter on the input | Commits the typed value; inside a form it also submits the form (native) |
| Enter or Space on a button | One step |
